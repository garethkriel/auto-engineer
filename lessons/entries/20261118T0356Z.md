## Task
Level 15 networking practice: stop-and-wait reliable transfer over UDP (`ae.udp`: Packet codec, ReliableSender, ReliableReceiver). Overlap check: benchmark names (miniserver, ratelimit, kvlog, cache, queue...) are TCP/HTTP servers or in-memory algorithms; a datagram ARQ protocol matches none.

## What worked
Making loss deterministic: the receiver takes a `Predicate<Integer>` drop policy (index n for the n-th received datagram, -1-n for the n-th outgoing ACK), so each test states exactly which packets are lost and asserts the exact transmission count (e.g. lost data -> 5 sends, two lost ACKs -> 5 sends, lost final ACK -> 3 sends with no duplicate delivery). 17 tests passed first run and on 6 clean repeats.

## What failed
Nothing failed (attempts = 1). One test comment was muddled while drafting; I recomputed the arrival sequence by hand and rewrote it before the final run.

## Root cause
No defect surfaced. Risks designed against: delivering a retransmitted chunk twice when only the ACK was lost (needs "seq < expected -> re-ACK, don't append"); a lost final ACK stranding the sender if the receiver returns immediately (needs a linger that re-ACKs duplicates of the last packet); decoding by buffer size instead of datagram length.

## Rule learned
For ARQ/UDP protocols, inject loss by index through a predicate instead of random drops, assert exact transmission counts, and give the receiver an explicit linger so the final ACK can be lost without failing the sender; decode with `DatagramPacket.getLength()`, never the buffer length.
