## Root cause
Comparator-relative methods (floor/ceiling/higher/lower) are easy to reason about in natural order only; expectations for a reversed comparator must be derived in comparator order. The 2 surviving mutants are equivalent: every rotation's new top has its size recomputed by `balance` before anyone reads it, and `floorKey`'s `c == 0` early return is only an optimisation because equal is the largest candidate.

## Rule learned
For ordered-map APIs with a custom comparator, write each floor/ceiling/lower/higher expectation by listing the keys in comparator order first. For a surviving mutant, name the later step that recomputes or dominates the mutated value before declaring it equivalent.
