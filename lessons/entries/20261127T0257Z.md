# 20261127T0257Z - ae.sf IEEE-754 soft-float

## Task
Level-20 capstone: binary64 arithmetic (add/sub/mul/div/sqrt/fma, long conversions, comparisons), exact decimal parsing and shortest round-trip formatting from scratch on raw `long` bits. Overlap check: `ls benchmark/java` (j01-roman .. j35-minisql) has no floating-point or number-formatting task; no existing skill covers IEEE rounding.

## What worked
- One exact representation (`BigInteger mag * 2^exp`) plus a single `round` routine made all six operations correct by construction; SoftDouble passed 13/13 JDK differential tests on the first run, including subnormals, ties and overflow edges.
- Oracles that are independent of my code: `Math.fma`/`Math.sqrt`, `Double.parseDouble`, JDK 21 `Double.toString`, and a BigDecimal `round(MathContext(n, HALF_EVEN))` + `parseDouble` brute-force for digit counts.
- Mutation pass: 16 of 16 non-equivalent mutants killed; the 6 survivors were equivalent (early-exit fast paths, a parity fix-up that runs anyway, an equivalent clamp bound, a no-op).

## What failed
First run: 4 DecimalTest failures (`123456.789` printed as `123456.78900000001`, 17 digits where 9 suffice).

## Root cause
In `Decimal.shortest` I wrote `powerOfTwoEdge = m.bitLength() == 53 && biased > 1`. Every normal double has a 53-bit significand, so the narrower lower interval half-width (the binade-boundary case) was applied to all normals, making the rounding interval asymmetric and rejecting valid shorter candidates. The correct test is `m == 2^52`. Tests caught it only because they compared with JDK on random bits and on a literal `123456.789`.

## Rule learned
When a special case applies only at a boundary value (power of two, min/max, empty), test equality with that exact value (`m == 1<<52`), never a property that every ordinary input also satisfies (`bitLength() == 53`); and keep one ordinary literal (`123456.789`) in the table next to the boundary literals so a too-broad condition fails loudly.
