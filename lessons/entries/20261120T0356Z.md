# Lesson 20261120T0356Z — erasure-coded blob store (level 20)

## Task
`ae.erasure`: GF(256) Cauchy Reed-Solomon codec plus a file-backed blob store with CRC-sealed shard headers, scrub/repair.
`benchmark/java/` has nothing on erasure coding (checked names in TASK.md).

## What worked
- Exhaustive MDS check (every erasure mask for six small (k,m) pairs) plus a carry-less-multiply oracle for all 65536 field pairs
  gave strong confidence with no hand-computed codewords. Mutation checks (Cauchy entry, field polynomial, putId vote,
  header consistency) were all caught; the last one only after I added a re-sealed forged-header test.
- Writing the stale-shard test first exposed that identical-length stale replicas cannot be told apart by length/CRC, so a
  per-put random id was added to the header before the implementation depended on the old layout.

## What failed
1. `System.arraycopy` with srcPos past the array end throws even for length 0 (empty/short blobs).
2. My randomised fault-injection test damaged shards cumulatively across steps without repairing, exceeding m bad shards.

## Root cause
1. I assumed a zero-length copy is always a no-op. 2. The test's invariant "damage <= m" was per step, but the state persists.

## Rule learned
Guard `arraycopy` with `n > 0` when the source offset may exceed the length. In fault-injection tests, state the damage budget over the
whole lifetime of the object (count currently-bad units via the status API before each injection). For replicated/striped
data, put a per-write version id in every replica header; length and CRC cannot reject same-size stale replicas.
