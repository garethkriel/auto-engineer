# 20261126T0957Z — ChaCha20-Poly1305, X25519, strict Ed25519 (ae.cc)

## Task
ChaCha20, Poly1305, the RFC 8439 AEAD, X25519 and strict Ed25519 in one package, with SHA-512 from the JDK. Overlap check: `benchmark/java/` names j01-roman … j35-minisql read; none is cryptography (skill `crypto-primitives` covers SHA-256/AES, a different set).

## What worked
- Tests first from RFC vectors (typed as literals) plus JDK 21 as differential oracle for the AEAD (250 random lengths), X25519 and deterministic Ed25519 signatures (byte-equal): 25 tests green on the first compile-clean run.
- Hand-derived Poly1305 edge vectors (acc = 2^130-2 mod p, wrap modulo 2^128) with the arithmetic written next to them.
- Per-byte bit-flip loops with an explicit control that opens, for ct, tag, aad and nonce.

## What failed
- Mutation pass (25 mutants): three survivors in `Ed25519.decode/verify` — `y >= p` to `y > p`, `S >= L` to `S > L`, and dropping the "x = 0 with sign bit set" rejection. One more survivor (`kc[31] &= 127` in X25519) is equivalent: the ladder reads bits 254..0 only. Also my harness split mutants on `|`, so `||` patterns needed a manual run.

## Root cause
Each strictness check was backed up by the signature equation itself: a non-canonical A/R or S = L + something fails the equation for a normal key, so "expects false" tests could not tell the range check from the maths. Same shape as earlier "guard masked by a later check" lessons, but here the masking is mathematical.

## Rule learned
For strict-verification code, build inputs where the equation holds and ONLY the strictness rule can reject: identity key (sB = R) for the negative-zero encoding, an order-4 point with S = 0 and a searched message (k ≡ 1 mod 4) for `y = p` and `S = L`, each next to a control differing only by the encoding. Use a different delimiter than `|` for mutation lists containing `||`.
