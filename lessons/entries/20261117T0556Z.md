## Task
Level 10 (concurrency): `conc.Parallel` with bounded fail-fast `mapOrdered`, `firstSuccess` (AllFailedException) and `withTimeout`. Overlap check vs `benchmark/java/` names (incl. ratelimit, cache, queue, counter): none is a parallel-executor/futures utility, so it was allowed.

## What worked
Acquiring the semaphore in the submitting thread made `limit 1` fully deterministic (exactly 3 tasks started when item 2 fails). A `CyclicBarrier(3)` inside tasks proves 3 really run together, while an `AtomicInteger` max proves the limit is never exceeded. `anyOf(allOf(futures), failure)` returns promptly when a later task fails.

## What failed
The first full run passed (19 tests) but repeating `mvn -B test` 5 times failed `firstFailureInTimeWins` in 3 of 5 runs: expected `first` but was `second`.

## Root cause
Test race, not a code bug: task "first" counted down a latch then threw, while task "second" woke on the latch and threw immediately, so it could record its failure before "first" reached `compareAndSet`.

## Rule learned
Concurrency tests must be run repeatedly (e.g. a 5-8 iteration `mvn -B test | grep "Tests run:"` loop) before being counted as passing; for "who wins" ordering tests, gate the intended loser behind a latch AND a delay (or a state the winner sets after it has recorded), never a latch alone that the winner releases before acting.
