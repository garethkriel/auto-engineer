# 20261126T0456Z — tar archive toolkit (ae.tar)

## Task
POSIX ustar/pax codec (`Entry`, `TarWriter`, `TarReader`) plus a traversal-safe `TarExtractor`, checked against GNU tar 1.35 in both directions. Overlap check: read `benchmark/java/` names (j01-roman … j35-minisql); none is an archive format.

## What worked
- An installed tool as oracle from the first test: GNU tar lists, extracts and creates archives that our code must agree with. It exposed four environment facts no spec reading would have: GNU rejects pax uid/gid above 32 bits, leaves devmajor/devminor as NULs, writes `ustar\0` + `00`, and restores a directory's mtime as soon as it meets a member outside it.
- Literal header bytes computed in Python (checksum as an unsigned byte sum with the field as spaces) plus a pax length table around the digit-count jump (body 98 -> record `101`).
- Per-rule crafted headers re-sealed with a valid checksum, each beside a control; flip-every-byte over an ASCII-only archive where the invariant is exact (611 data bytes survive, every other byte is rejected).
- A 65-mutant pass: 51 killed at once; 14 survivors, 11 were test gaps (checksum byte 155, 12-byte header tail, record-length minimum, pax cap message, no-terminator octal, reversed parent/file conflict, dangling on-disk symlink, out-of-range mtime, long mtime text, mode cap, digit cap) and are now killed; 3 are justified.

## What failed
- First test run: 5 failures, all test-side: a hand checksum literal that included device fields the writer leaves NUL (5746 instead of 5074), random ids/times beyond what GNU tar reads, and JVM file-name encoding (`sun.jnu.encoding` is ASCII under the POSIX locale, so `Path.of("é")` throws `InvalidPathException`). Second run: one GNU-vs-ours tree difference caused by interleaved children (see Root cause). Third run passed (attempts = 3).
- Mutation survivors where two checks reported the same word: the test asserted `"mode"` but both the reader's cap and the `Entry` constructor mention mode, so changing the cap went unnoticed.

## Root cause
Oracles and fixtures encode assumptions about the oracle's limits (32-bit ids, directory time restore heuristic) and about the environment (file-name charset). Where two guards can produce an error mentioning the same field, a message-substring assertion cannot tell which fired. The 70-line extractor also showed that lexical `..` normalisation of symlink targets is unsound once another archive link can change what a name means (`s -> .` then `t -> s/..`).

## Rule learned
When an external tool is the oracle, probe its limits first and generate fixtures inside them (ids <= 2^32-1, children contiguous after their directory); keep non-ASCII file names out of `Path` APIs (build them with a UTF-8 shell script on stdin) unless `sun.jnu.encoding` supports them. Give every guard a message that names the rule (`exceeds 07777`, `invalid octal field size`, `cap`, `too many digits`) and assert that exact phrase, so a mutant that moves the boundary onto a different guard still fails. For symlink-safe extraction allow `..` only as a leading run no longer than the link's depth, validate the whole entry list (against itself and the disk, without following links) before writing anything, and test a reversed-order conflict (`a/b` then `a`).
Survivors justified as equivalent: splitPoint `i >= 1` (index 0 is never `/` because names have no leading slash); `size > avail` in `body()` (implied by `padded(size) > avail` because the archive length and every block offset are multiples of 512); applying directory metadata outermost-first (only observable by a non-root user with a parent lacking the x bit; the test for it is skipped under root).
