## Task
Strict binary decoder (LEB128, sections, UTF-8 names), spec-style validator with the stack-polymorphic rule, lowering to flat branch-resolved code, an interpreter with traps/fuel, and tests: literal vectors, per-opcode tables, programs, truncation and byte-flip robustness, a BigInteger-oracle differential test and a 107-mutant pass. Overlap check: `ls benchmark/java` (j01-roman .. j35-minisql) has text evaluators (j07-expr, j28-script) but no binary decoder/validator/stack machine, and no skill mentions wasm.

## What worked
Writing TASK.md with the exact subset and semantics first (fuel units, depth limit, effective-address rule, message substrings) so tests could assert messages. Literal LEB128 vectors (Wikipedia examples) found the real decoder bug at once. A differential oracle written with `BigInteger` modulo 2^w (no JDK integer helpers) agreed with the interpreter on 7500 random evaluations after the oracle itself was fixed. The truncation loop (non-boundary prefixes must be MALFORMED) and the byte-flip loop (mutated modules are instantiated and run with fuel; only `ModuleException`/`Trap` may appear) cost little and need no hand-written cases. Mutation pass: 102 of 107 mutants killed by failing tests, 4 by timeout (a wrong branch target loops forever), 1 equivalent.

## What failed
- Four of the seven first-run failures were my own test defects: a trailing comma in a `Stream.of`, an `i64.clz` row declared with an i32 result, a wrong s33 expectation (a last byte of `0x10` has the sign bit set, so it is -2^32, not 2^32), and `m.mem()` encoding the vector count twice. The decoder bug was real: signed LEB128 sign-extended from the declared width instead of from the last byte read, so `0x7F` decoded as 127.
- Differential test: "expected 0 but was 1" came from the ORACLE. In `binary(int w, ..., int outW)` the anonymous `Node` subclass has a field `w`; inside its `eval` the name `w` meant the inherited field (output width 32), not the method parameter (operand width 64), so `le_s` compared 64-bit values as 32-bit. Found only after tracing each oracle operation for the one failing case.
- Mutation survivors revealed missing boundary tests: vec count exactly one over the remaining bytes, memory max 65537, start function with parameters, export index equal to the count, function-type index equal to the type count, code-body size one over the section, `return` not checking its operand, `else` not resetting the polymorphic flag, store bounds one byte over, `store8` writing a second byte (the neighbour was zero), i32.load losing its sign, br_table consuming no fuel, call-depth and operand-stack limits off by one. Two survivors were dead code instead: the `bits`-width sign extension in `Reader.leb` and the `b == -1` special case of `rem_s` (Java's `%` already returns 0); I deleted both.
- My first mutation list had a no-op mutant (dead code inserted after a throw) and a `while (false)` that fails to compile; both were rewritten.

## Root cause
Hand-written fixtures and helper code were checked only by running them, and several guards were tested only with a value far past the limit instead of exactly one over. Name shadowing between an anonymous class's inherited field and a captured parameter silently changed an oracle. Sign-extension logic was written from the declared bit width instead of from what was actually read.

## Rule learned
(1) In oracle/generator helpers that build anonymous subclasses or lambdas, never give a parameter the same name as an inherited field (`w`, `size`, `kind`); name them `inW`/`outW`, and when an oracle disagrees print a per-operation trace for the one failing case before touching the system under test. (2) Variable-length integers: sign-extend from the last byte read, test the published literals in both signs (`-1` as `0x7F`, `-123456` as `C0 BB 78`) and the s33/s64 extremes. (3) For every limit, count or index guard write the two tests exactly at and exactly one past the boundary, and for every memory write assert the neighbouring bytes are unchanged (zero neighbours hide a wrong width). (4) A surviving mutant that cannot be killed by any input means dead code: delete it rather than keep an equivalent branch.
