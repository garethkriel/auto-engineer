## Task
Level 17 (larger design): event-sourced shopping cart in four packages (domain, port, adapter, app): sealed `CartEvent`, immutable `Cart` aggregate, `EventStore` port with optimistic concurrency, `InMemoryEventStore`, `CartService`, `SalesProjection`. Overlap check: benchmark has j09-bank, j19-allocate, j32-fsm, j33-pricing, j24-queue; none shares the event-store/projection core.

## What worked
Writing the design (dependency direction, rules, read model) in TASK.md first, then tests. Anchor tests were literal event lists and positions; a 60-seed randomised test compared the incremental projection to a naive recompute from aggregates and to a fresh catch-up. `mvn -q -B clean test` passed on attempt 1: 29 tests, 0 failures; the concurrency test class passed 5 extra runs.

## What failed
Nothing failed at runtime. Two drafted assertions had placeholder expressions (`x + 0 * x` and a loop hunting for an overflow); I caught them on re-read and replaced them with a literal two-lines-fit / third-overflows case (2*(2^31-1)^2 < 2^63).

## Root cause
Awkward-to-state expectations tempt me to write expressions that mirror code or search loops; they would hide mistakes. Pure `decide` functions plus a service-level spy store made the port boundary testable without mocks.

## Rule learned
For event-sourced designs: keep `decide` pure and `apply` a fold, append with the version that was read, test the stale-version race by a decorating store that sneaks a write between read and append, and verify projections against an oracle recomputed from aggregates, not from the projection's own logic.
