# 20261127T0356Z — ae.cal calendar systems toolkit

## Task
Level-20 capstone: calendar conversions over epoch days (proleptic Gregorian/Julian, Julian-to-Gregorian hybrid with the 1582 gap, tabular Islamic), month arithmetic, ISO week/ordinal dates and Easter. Overlap check: read `benchmark/java/` names (j20-cron, j25-bizhours, j16-ranges ...); none implements calendar conversion, only scheduling/business-day logic.

## What worked
- One pivot (epoch day via JDN) and floor-division integer algorithms: the whole Gregorian range (+-2M days) matched `LocalDate`, Julian and hybrid matched `GregorianCalendar` over years 1..3000 on the first run.
- JDK oracles for the structure, hand-computed literals (Islamic epoch 1 Muharram 1445 = 2023-07-19 derived from the 10631-day cycle) for the parts the JDK cannot give.
- A 22-mutant pass (21 killed, 1 equivalent) exposed three real test gaps.

## What failed
- First run: 6 failures. Five were my own wrong expectations (2000-03-01 epoch day off by one, `2024-02-29 - 2 months` written as the 31st, a 5th Thursday in Feb 2024 which does exist, Easter 1954 misremembered as 25 April, and a placeholder-style expression I had to delete). One was a real bug: `isValid` bounded the day by the month length (21) for HYBRID October 1582, which has day numbers 1-4 and 15-31.
- Later, my first Gauss Easter oracle applied its "26 April -> 19 April" exception on a March-based day count wrongly (compared with 26 instead of 57).
- Mutants that survived: Islamic inverse offset (10646 -> 10645), Islamic month start `ceil` -> `floor`, `parse` length check `==8` -> `>=8`, Gregorian Easter correction `(b+8)/25` -> `(b+7)/25`.

## Root cause
- The gap month has a *length* (21) different from its *largest day number* (31); one helper served both purposes.
- Tests only touched the Islamic calendar at year starts and a few literals, so self-consistent errors in month starts and the inverse (round trips stay consistent when both directions share the same wrong table) went unnoticed. Easter was only tested on years from memory, none in 1700-1799 where `(b+8)/25` first changes.
- Hand-recalled literals (1954 Easter, 2000-03-01) were wrong; I did not derive them.

## Rule learned
- Calendars with irregular spans: separate `length` from `maxDayNumber`; add a walk test that every consecutive epoch day yields either day+1 or day 1 of the next month with `prev.day == last day`, for every system, including negative years.
- A round trip cannot detect a wrong table shared by both directions: add contiguity checks (month start + length = next month start) and a differently structured oracle (Gauss vs Meeus for Easter) swept over the entire supported range.
- Derive literals from counts (cycle lengths, 10957 days to 2000-01-01) and write the arithmetic in a comment; never type dates from memory. Gauss-style exception rules must be applied in the same unit as the base count (March-based).
- Parsers with fixed widths: include an input that is a valid prefix plus trailing digits.
