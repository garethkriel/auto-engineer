## Task
Level 8 (command pattern): `Editor` with undo/redo over `Command`s whose `apply` returns their inverse (insert/delete/replace/atomic macro), bounded history and dirty tracking. Overlap check: benchmark/java names (roman, wordfreq, lru, csv, intervals, lcs, expr, graph, bank, counter, streams, fileindex) have nothing to do with command/undo, so no overlap.

## What worked
18 tests written first, all passing on attempt 1 (`Tests run: 18, Failures: 0`). Having `apply` return the inverse removed the need for stateful commands that remember deleted text, and made undo and redo the same code path (`step(from, to)`).

## What failed
Nothing failed. The risky design point was dirty tracking: a stack-depth "saved index" breaks when history is truncated or edits diverge after undo.

## Root cause
Position-based save markers are invalidated by truncation/branching; monotonic revision ids are not. A test (`divergingHistoryAfterSaveStaysDirty`) targets exactly that case.

## Rule learned
For undo/redo, make commands return their inverse, validate before mutating so a failed execute leaves document and redo stack intact, and track "saved" by unique monotonic revision ids, never stack depth.
