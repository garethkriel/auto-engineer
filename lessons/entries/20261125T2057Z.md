# 20261125T2057Z — cluster reconciler (level 20)

## Task
Deterministic Kubernetes-like reconcile loop: kubelet, deployment controller with maxSurge/maxUnavailable rolling updates, most-free-cpu scheduler, node failure. Overlap check: read `benchmark/java/` names; none is a controller/scheduler simulation.

## What worked
Fixing the tick phase order and each controller rule in TASK.md before any test; a hand-derived 5-tick rolling-update trace as the anchor test; invariant assertions (total <= replicas+surge, running >= replicas-unavailable, bound cpu <= capacity) after every tick; five single-rule mutants all failed the suite.

## What failed
First run: the "new version never fits" test failed (`expected 2 but was 3`). I had asserted two pods remain, but surge 1 lets the controller create a second unfit new pod (total = replicas + surge = 3). I also first wrote that scenario with same-size pods, where the freed slot lets the new pod fit and the rollout completes, so no stall happens at all.

## Root cause
Test defect: expectations for a stalled state were written from intuition instead of running the controller formula `min(replicas - new, replicas + surge - total)` by hand per tick; a stall needs a new pod that is larger than the largest free hole.

## Rule learned
For stall/blocked scenarios in rollout-style controllers, trace the creation formula tick by tick (including how many unfit pods surge allows) and make the stall by construction (new pod larger than any free hole) before writing the final-state assertions.
