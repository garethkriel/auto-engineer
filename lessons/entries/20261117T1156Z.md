# 20261117T1156Z — bounded blocking ObjectPool (level 10)

## Task
`pool.ObjectPool<T>`: bounded, blocking resource pool with lazy creation, validator, invalidate, close, timeouts. Overlap check against `benchmark/java/` names: no pool (ratelimit, cache, queue are different).

## What worked
Writing the accounting invariant first (`total = idle + borrowed + reserved-for-creation`) and the rule "callbacks run outside the lock". Passed on the first run (16 tests); repeated 6 more times, all green. A stress test asserting peak concurrency <= max, no object shared between borrowers, and created == destroyed-once caught the classes of bugs that matter.

## What failed
Nothing failed. Only a mild hazard: a candidate taken from idle must stay in the `borrowed` set while it is validated outside the lock, otherwise `close()` or another thread could lose track of it.

## Root cause
n/a (no failure). The design risk was slot leaks on every exceptional path (factory throws/returns null, validator throws, destroyer throws, close during creation).

## Rule learned
For pools/semaphores: reserve the slot before calling user code and release it in a catch on every exit path, and test each exit path (factory failure, null, validator exception, destroyer exception, close mid-creation) by asserting `size()` afterwards.
