## What worked
- Documenting the byte layout in the class Javadoc and TASK.md first let me hand-build images in a test helper (`Img`, with an independent bit-by-bit packer) and craft one defect per test, each next to a control image that loads.
- Size arithmetic written as literals in comments (single value: PLAIN 17, FOR/DELTA 18, DICT 22, RLE 25) made `encodeBest` expectations checkable by hand.
- Zero-width packing (width 0 for constant/one-entry dictionaries) falls out of one `get`/`pack` implementation; differential scans over 5 encodings x 6 ops x probes incl. MIN/MAX/±1 caught nothing because pruning (`Op.prune`) was unit-tested with a literal verdict table first.
- 20-mutant hand check: 17 killed, 2 equivalent/no-op (a redundant `runs > n` guard that run-sum and byte-count checks also cover; a `+ 0 * rows` no-op), 1 real gap.

## What failed
- Attempt 1: 30/31 passed. `encodeBestPicksTheSmallestShape` expected RLE for a 1000-element constant column, but FOR with width 0 is 18 bytes and RLE is 25. Test defect, no code defect.
- Mutation: dropping the "FOR base must equal the minimum" validation survived; no crafted image had a canonical width but a non-minimal base.

## Root cause
I reasoned about which encoding "should" win from its name (constant data -> RLE) instead of computing the byte sizes from the layout; zero-width packing makes FOR beat RLE for constants. The surviving mutant is the same pattern in the validator: each canonical-form rule (width, padding, base) needs its own crafted image, and I had written images for width and padding but not base.

## Rule learned
- Derive "which variant wins" expectations from the layout's byte arithmetic (write the sizes as literals in a comment), never from the variant's name or intuition.
- For a strict (canonical-form) decoder, list every redundancy in the format (width, padding, base, sort order, run lengths) and write one crafted, CRC-resealed image per redundancy plus a control that differs only by that defect; kill-check by deleting each rule.
- A decoder for formats where a field can be tiny but expand hugely (width 0, RLE) needs an explicit row cap (`MAX_ROWS`) and a test for it, in addition to checking sizes before allocating.
