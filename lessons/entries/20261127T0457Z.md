## What worked
- Writing literal expectations first: a hand-traced replacement-selection example (M=3, 9 records -> runs of 5 and 4), a (runs, fanIn) -> merge-levels table checked against repeated ceiling division, and "reverse-sorted input gives exactly ceil(n/M) runs" gave exact structural checks beyond the differential `List.sort` oracle.
- Failure injection (codec/comparator/consumer throwing at the n-th call) plus "temp dir is empty" caught the leak class without needing to know where the leak could be.
- All 33 tests passed on the first run; a 14-mutant pass killed 13 at once.

## What failed
- Nothing failed in the run. One mutant survived: replacing the immediate deletion of consumed run files (`deleteAll(group, live)`) with a no-op, because the final `finally` cleanup deletes everything anyway, so end-state "dir is empty" tests cannot see it.
- I also left a junk loop (`lastRunSeq`, `assertNotNull(p)`) in a first draft of the stability test and had to rewrite it before running.

## Root cause
- The survivor: an eager-release property (disk use bounded during the merge) and a final-cleanup property (nothing left at the end) look the same to an end-state assertion. Only a probe taken while the sort is still running (file count inside the consumer at the first output) separates them.
- The junk loop came from writing a cross-run check by feel instead of stating the invariant first ("per key, seq increases when scanning runs in order").

## Rule learned
- Resource-release tests need two assertions: nothing left after the call, and a probe during the call (e.g. count files in the consumer callback at the first output) when release is supposed to be eager.
- For external-sort / run-based designs: state the invariant ("per key, arrival order is preserved across runs") before writing the test, derive merge-level counts from repeated ceiling division, and keep stability by merging consecutive runs with ties to the lower source index.
