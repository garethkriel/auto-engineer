## Task
Level 8 (design patterns): chain-of-responsibility middleware `Pipeline` with `Router`, `requireToken`, `recover`, `trace` and a TTL `cacheGet` middleware. Overlap check: benchmark/java names (roman, wordfreq, lru, csv, intervals, lcs, expr, graph, bank, counter, streams, fileindex) do not involve routing or middleware; the TTL cache has no capacity or eviction order, so it is not an LRU.

## What worked
Folding the middleware list from the end into nested `Handler` lambdas kept `Pipeline` immutable in ~10 lines. An injected `Clock` made TTL boundary tests (9s hit, exactly 10s miss) deterministic. 18 tests, final `Tests run: 18, Failures: 0`.

## What failed
Attempt 1: 2 of 18 tests failed (`recoverOnlyCoversInnerMiddlewares`, `fullStackComposes`). Both were test defects: I wrote the `use(...)` calls in the opposite order from the specified "first used = outermost" rule.

## Root cause
Ordering semantics of a builder (outermost-first vs innermost-first) are easy to invert when writing the tests; I reasoned about "wrapping" order instead of rereading my own TASK.md. Code was right, expectations were wrong.

## Rule learned
For wrapper/middleware chains, write a single ordering test first, then derive every other test's `use(...)` order from it and annotate the layer order in a comment (e.g. `// outermost: auth, recover, trace`) before asserting on logs or which layer catches what.
