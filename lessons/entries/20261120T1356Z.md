## Task
Level 20 capstone: `ae.minilang`, a tiny integer language with lexer, parser, checker, tree interpreter, AST optimiser, bytecode compiler, stack-depth verifier and VM, run through four interchangeable engines. Overlap check: no language-implementation task in `benchmark/java/` or `skills/java/`.

## What worked
- TASK.md fixed the semantics before code (scoping, params share the body scope, depth limit exactly 100 frames, error kinds, optimiser may not drop anything that can throw or call), so hand-computed tests agreed with code.
- Tests before code for each layer; the front end, arithmetic, verifier and execution tests all passed on the first run.
- A seeded generator building ASTs (not strings) gave valid programs by construction; its outcome mix was measured before asserting minimums (574 clean, 527 DIV_ZERO, 399 OVERFLOW of 1500).
- Cross-checks that cost little: printer round trip, optimiser idempotence, "optimised bytecode never longer", verifier on every compiled program.
- Mutation kill-check: 11 of 12 killed; the survivor (`Long.MIN_VALUE % -1` special case) is equivalent in Java.

## What failed
- Attempt 1 had two test-side defects: the generator's block helper cleared the "declared here" set for function bodies, so a `let` could redeclare a parameter (the Checker correctly rejected 392 of 1500 programs), and an optimiser test expected `{ print 2; }` although the fixpoint pass flattens declaration-free blocks to `print 2;`.

## Root cause
The generator modelled scopes by hand and the function-body scope (params plus body in one scope) was a special case I forgot; the "generated input is valid" test caught it immediately. For the optimiser, I wrote the expectation from one pass instead of from the documented fixpoint behaviour.

## Rule learned
- Language/compiler work: put one shared arithmetic definition behind all engines, test it against BigInteger, compare engines on (output, error kind), and give the bytecode a verifier that is tested with crafted one-defect images plus a control.
- Optimisers: never fold an expression that can throw and never drop one that can call; test each such rule with a case that would change behaviour, and assert idempotence on generated programs.
- Program generators must mirror the checker's scope rules exactly; keep a "generated programs are valid" test as the first failing signal.
