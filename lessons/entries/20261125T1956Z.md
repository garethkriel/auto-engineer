# 20261125T1956Z — symmetric crypto primitives from scratch

## Task
`ae.crypto`: streaming SHA-256, HMAC, HKDF, PBKDF2, AES (computed S-box) with CBC/CTR/GCM and a constant-time compare. Overlap check: I read the 35 benchmark directory names (j01-roman .. j35-minisql); none is a hash/MAC/cipher task, and no existing skill implements one (they only call `MessageDigest`).

## What worked
Design table in TASK.md, then tests first: published literals (FIPS, RFC 4231/5869, NIST GCM, PBKDF2) plus randomized JDK differentials over the padding-edge lengths (0..200 for SHA-256, key lengths 0/63/64/65/131 for HMAC, all dkLen around 32 for PBKDF2, aad x plaintext grids for GCM). Tamper tests flipped every bit of ciphertext, tag and AAD with an untampered control. All 45 tests passed on the first `mvn -q -B clean test` (attempts: 1).

## What failed
Nothing in the test run. A 20-mutant pass killed 17 at once. Survivor 1 (`hkdfExtract` empty salt -> 1 zero byte instead of 32) is equivalent: HMAC zero-pads keys, so both keys give the same MAC. Survivor 2 (`nk > 6` -> `nk > 7`) was a badly chosen mutant: AES nk is only 4, 6 or 8, so the sets are identical; the replacement mutant `i % nk == 5` was killed by the AES-256 vector.

## Root cause
Survivors came from mutants that change a representation without changing the value the next stage reads (zero-padding in HMAC; a threshold between values the domain never takes). The cause is mutant design, not a test gap.

## Rule learned
Before counting a survivor as a gap, list the domain values the mutated expression can see (AES nk in {4,6,8}) and what the consumer does with the changed value (HMAC pads keys with zeros); if both sets are unchanged it is equivalent, and pick a replacement mutant that moves a value inside the domain. For primitives with published vectors, pair literals with a JDK oracle over every padding-edge length.
