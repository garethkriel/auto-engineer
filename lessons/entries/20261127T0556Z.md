# 20261127T0556Z — ae.dec arbitrary-precision decimal

## Task
Level-20 capstone: `Dec` (BigInteger unscaled + int scale) with parse, arithmetic, `setScale`/`round` in all 8 rounding modes, `divide` with BigDecimal's preferred-scale rule, `divideExact`, correctly rounded `sqrt`, and `toString`/`toPlainString`. Overlap check: listed `benchmark/java/` (j01-roman .. j35-minisql): no numeric-type task; `bigint-from-scratch` has no scale/rounding. Previous rejections were for duplicated domains (datalog, patch-toolkit), so I picked a domain with no practice round or skill.

## What worked
- One shared `applyRounding(q, rem, den, sign, mode)` used by `setScale`, `round`, `divide` and `sqrt`, so the eight modes were written once and tested through four entry points.
- Differential tests against `BigDecimal` with seeded generators biased toward digits 0/5/9 (ties, carries, trailing zeros), plus counters asserting the mix (non-throwing divisions > N/2, exact roots > 100).
- All 79 tests passed on the first run (attempt 1); a 17-mutant pass killed 16 mutants once tie tests were added.

## What failed
- Nothing failed at runtime. The mutation pass first showed `HALF_DOWN` in `sqrt` surviving: no fixture hit an exact half-way root (sqrt(6.25) = 2.5 at precision 1). The first draft of `toPlainString` also had a nonsense zero-branch expression and `sqrt` assumed a non-negative power of 100; both were caught by rereading before the first run.
- One test draft contained a placeholder ternary (`RoundingMode.CEILING.equals(null) ? ...`), removed before running.

## Root cause
- Random differential tests rarely hit measure-zero events: an exact tie in a square root needs a radicand that is a perfect square of a half-integer, which random digits almost never produce. Only a hand-picked fixture (6.25, 12.25) separates `>` from `>=`.
- The `sqrt` negative-shift bug came from reducing `u*100^j` to an integer without thinking about j < 0 (more input digits than twice the precision); the fix was to carry the radicand as a num/den pair.

## Rule learned
- For rounding code, add a hand-built exact-tie fixture per entry point (setScale, divide, sqrt), because random inputs almost never produce exact ties for non-linear operations; confirm with a `>` to `>=` mutant per mode.
- When an algorithm scales an operand by `10^k` to reach a target precision, treat both signs of k explicitly (multiply the numerator or the denominator) and keep the remainder test in terms of the same num/den pair.
