# 20261125T1656Z — geohash toolkit

## Task
`ae.geohash`: encode/decode (bit-interleaved base32), 8-direction neighbours with antimeridian wrap and pole stops, sorted box cover (including boxes crossing the antimeridian), haversine. Overlap check: the 35 benchmark directory names (j01-roman .. j35-minisql) contain no geospatial/geohash task; existing skill spatial-quadtree is a point index, not a text encoding.

## What worked
Index-based design (cells addressed by integer ix, iy) made neighbours and cover pure arithmetic. Literal known hashes (ezs42, u4pruydqqvj, corner cells) plus a brute-force enumeration oracle for cover found a real bug quickly.

## What failed
Attempt 1: 4 failures. Attempt 2: 1 failure. Attempt 3: all 20 pass (`Tests run: 20, Failures: 0`). The implementation was drafted before the tests (process slip); the tests were then written against it.

## Root cause
One real bug: for a wrapped box (west > east) whose two edges fall in the same or adjacent cells, width = (cells - x0) + x1 + 1 exceeded the row width, so the cover listed a cell twice. The oracle (enumerate all cells, test intersection) caught it with a random box. The other three failures were test defects: a published-neighbour literal recalled from memory (S/W of ezs42), arithmetic on cell sizes (25 bits = 13 lon + 12 lat bits, not 14/13), and pole-row cells at precision 1 having no north neighbour in an invertibility test.

## Rule learned
For wrap-around ranges, clamp the computed span to the ring size and test a box narrower than one cell that "wraps"; derive expected literals from bit layouts (count lon/lat bits from the length) instead of remembering published values; when a property holds only away from boundaries (neighbour invertibility), exclude boundary rows by construction (min precision) and say why in a comment.
